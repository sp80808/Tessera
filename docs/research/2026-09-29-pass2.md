# Research pass 2 — token transport, active context, ownership graphs, incremental queries

Date: 2026-09-29

This pass converts recent research into implementation hypotheses for Tessera. It complements the core dossier rather than replacing it.

## Executive synthesis

The strongest combined direction is not "make Rust syntax shorter".

Tessera should instead separate four concerns:

1. **TC canonical source** — stable, deterministic, dense language syntax.
2. **TMT model transport** — optional reversible compiler-generated shorthand selected for a model/task/tokenizer.
3. **TIR semantic model** — explicit types, effects, moves, borrows, capability state, control/data relations.
4. **TCG active context workspace** — task-scoped, graph-derived context managed as an explicit harness capability.

The compiler/query database should be the common substrate for TIR and TCG. This prevents a second, stale semantic index from growing beside the compiler.

## 1. Token efficiency: canonical syntax and model transport should be separate

### ShortCoder

ShortCoder (arXiv:2601.09703) applies ten AST-preserving Python simplifications and reports 18.1% token reduction from its syntax simplification stage, while its trained system reports improved generation efficiency without sacrificing benchmark correctness in the reported experiments.

Transferable idea:
- mine transformations at the AST/TIR level;
- validate equivalence mechanically;
- measure model tokens, not characters;
- preserve an exact inverse or canonical semantic normal form.

Tessera consequence:
**syntax simplification should be a benchmarkable compiler pass**, not manual code golf.

### Token Sugar

Token Sugar (arXiv:2512.08266) goes further than syntax cleanup: it mines frequent token-heavy code patterns, assigns reversible shorthands and trains models on the sugarized representation. The paper emphasizes deterministic reversibility and an unambiguous shorthand namespace.

Transferable idea:
- frequently recurring semantic patterns may deserve compact handles;
- the shorthand need not itself be executable source;
- pattern IDs can be atomic from the model's point of view.

Tessera consequence:
do not permanently pollute TC grammar with hundreds of sugars. Put experimental high-cardinality shorthand in **Tessera Model Transport (TMT)**. TC remains small and stable.

### CodePromptZip / compiler-mediated compression

CodePromptZip (arXiv:2502.14925) and compiler-tokenized compression work reinforce a broader pattern: program analysis can decide which code units are low-value for a particular model task.

Tessera consequence:
TMT may have task-specific views:
- generation,
- repair,
- explanation,
- repository retrieval,
- diagnostics.

### TokDrift

TokDrift (ACL 2026) shows that semantics-preserving naming/formatting rewrites can alter code-model behavior, including large coding models. Grammar-aligned pretokenization did not uniformly remove the problem.

Tessera consequence:
- one canonical TC spelling;
- benchmark cross-tokenizer segmentation stability;
- do **not** assume lexer boundaries alone solve model-token misalignment;
- transport profiles need empirical validation per model family.

## 2. Grammar-constrained generation should be a harness/compiler interface

XGrammar, TreeCoder, CFGZip and related constrained-generation work show that grammar-aware generation can be efficient enough to use during code synthesis. Recent work focuses on precomputing relationships between model tokens and grammar/parser states rather than reparsing every possible token naively.

Tessera opportunity:

```
TC grammar
  -> incremental parser state
  -> model-token compatibility table
  -> valid token/class mask
  -> generation
  -> ordinary Tessera parser/type/effect checks
```

This should remain optional. A model must still be able to emit ordinary TC text.

Potential value:
- fewer syntax repair turns;
- extremely compact syntax can be safer to generate;
- grammar evolution can be tested directly against decoding overhead.

Important caveat:
syntactic constraint does not imply type/effect/ownership correctness. Later experiments can test incremental semantic constraints, but the first implementation should constrain grammar only.

## 3. Context management: active workspace beats passive accumulation

### Context as a Tool (CAT)

"Context as a Tool: Context Management for Long-Horizon SWE-Agents" (arXiv:2512.22087 / Findings ACL 2026) treats context maintenance as an explicit callable action. Its workspace distinguishes stable task semantics, condensed long-term memory and high-fidelity short-term interaction. The reported SWE-Bench Verified result is 57.6% for SWE-Compressor, outperforming the compared static/ReAct baselines in that setup.

Tessera consequence:
TCG operations should be agent tools, not only invisible harness heuristics:

```
ctx.pin(...)
ctx.condense(...)
ctx.drop(...)
ctx.refresh(...)
ctx.project(...)
ctx.explain(...)
```

Every operation should leave an auditable context-state transition.

### RepoMirage

RepoMirage (arXiv:2605.26177) perturbs repositories to force cross-file structural reasoning. The paper reports average performance falling from 66.8% on the original issue-resolution setting to 25.3% on explicit perturbation-derived context tasks, and observes "exploration drift": agents read more without forming useful structure. Supplying structural hints improves results; RepoAnchor therefore separates structure exploration from solving.

Tessera consequence:
the TCG context packet should include **pre-composed structural paths**, not simply more files.

Examples:
- caller -> callee -> invariant -> test;
- feature -> dependency -> API contract -> affected symbol;
- diagnostic -> ownership edge -> conflicting operation -> repair candidates.

### Minimal context / context files

Recent 2026 work on coding-agent context reports that highly compressed task-specific context can approach much larger whole-file contexts at a fraction of token cost. Other controlled studies report limited or inconsistent correctness gains from always-on repository context files.

Tessera consequence:
AGENTS.md remains useful for durable policy, but semantic/task context belongs in **dynamic projections**. Never assume "more persistent instructions" is equivalent to better context.

## 4. Ownership: graph the capabilities, not just lifetime prose

### From Linearity to Borrowing

Wagner et al., "From Linearity to Borrowing" (DOI:10.1145/3764117), builds borrowing incrementally from a linear system:
1. owned linear memory,
2. immutable borrows,
3. lexical lifetimes,
4. reborrowing,
5. mutable borrows.

The paper establishes semantic type soundness and a model supporting termination and memory reclamation for the calculus.

Tessera consequence:
this is an excellent order for the v0 semantic implementation. Start with a small sound calculus rather than implementing every Rust convenience.

### Place Capability Graphs

Place Capability Graphs (arXiv:2503.21691) represent Rust ownership/borrowing with a flow-sensitive directed hypergraph. Place nodes carry capabilities such as exclusive/read/write/none, and edges capture movement/borrowing relationships.

Tessera consequence:
TIR should expose a **Tessera Capability Graph (TCap)** as a derived view.

Proposed capabilities:

- `E` — exclusive: read/write/move/borrow;
- `R` — shared read/borrow;
- `W` — assignment/write capability where semantically valid;
- `0` — no current access;
- optional later capabilities for atomic/unsafe/FFI authority.

TCap can power:
- borrow checking diagnostics;
- human expansion;
- agent context;
- program analyses;
- visualization;
- proof obligations around unsafe blocks.

The compiler remains authoritative; TCap is not agent-inferred.

## 5. Incremental architecture: one dependency graph for compiler + context

Rust's incremental compilation and Salsa both center computation around deterministic queries and explicit dependencies. Salsa tracks which inputs a query reads and memoizes results; rustc's red/green dependency approach similarly seeks to recompute only affected queries.

Tessera should exploit this twice:
- compiler analysis;
- context/evidence invalidation.

Proposed query chain:

```
source(file)
 -> lex(file)
 -> cst(file)
 -> ast(file)
 -> module_items(file)
 -> resolve(symbol)
 -> infer(symbol)
 -> effects(symbol)
 -> capability_graph(symbol)
 -> tir(symbol)
 -> call/data graph(symbol)
 -> tcg_projection(task)
 -> tmt_pack(task, model)
```

External facts enter as explicit **evidence inputs**, never hidden I/O inside tracked compiler queries:

```
evidence(id) = immutable/revisioned input
verified_claim(id) = query(evidence, project state)
```

A lockfile change can therefore invalidate dependency-context claims without re-typechecking unrelated functions.

### Lossless syntax trees

rust-analyzer's Rowan-style red/green syntax architecture is especially relevant because Tessera requires:
- exact source preservation;
- error-tolerant parsing while editing;
- stable source ranges;
- cheap structural reuse;
- deterministic TC formatting.

The prototype should evaluate Rowan-like lossless trees versus a simpler hand-rolled CST before committing.

## 6. Proposed architecture after this pass

```
                    external evidence
                          |
                          v
TC source -> lossless CST -> semantic query DB -> TIR/MIR -> backend
                |               |    |             |
                |               |    +-> TCap      +-> Cranelift/LLVM
                |               +------> TCG
                |                        |
                +-> formatter            +-> task projection
                                             |
                                             v
                                      TMT/context packet
                                             |
                                      LLM / coding agent
```

Key rule:
**TMT and TCG may change per model/task; TC/TIR semantics may not.**

## 7. New falsification tests

### Transport
- Does TMT reduce total tokens-to-correct-patch, not just prompt length?
- Does model-specific shorthand cause cross-model brittleness?
- Is every transform exactly reversible to equivalent TIR/TC?

### Constrained generation
- Does grammar masking reduce syntax repair turns enough to offset decoding overhead?
- Does it harm model choice when a grammar prefix admits many tokenizations?

### Active context
- Does explicit context management beat fixed graph top-k and always-on context?
- Does path composition reduce "integration width" at equal token budget?

### Capability graph
- Can TCap explain all v0 borrow-check failures with local graph deltas?
- Is TCap materially smaller than verbose lifetime diagnostics in model tokens?

### Incremental database
- Does editing one function avoid recomputing unrelated TIR/TCG projections?
- Can evidence invalidation share the same dependency machinery without introducing nondeterministic compiler queries?
